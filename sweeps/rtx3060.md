# Ternary Bonsai 2 27B + grafted Qwen 3.8 MTP head, RTX 3060 12GB

All numbers from one RTX 3060 12GB, one session (Sep 19 2026), the same node,
`--parallel 1` on every arm, thinking off, q4_0 K/V cache, flash attention on,
131072 context unless stated. Client tok/s are `probe.py` (streamed content
deltas, time to first token excluded), medians of 3 runs per prompt. Draft
acceptance is the server's `draft acceptance` print_timing line for that run.
Baseline arm and flag arm ran on the same merged file, flag off vs flag on.

Binaries:

- prebuilt: PrismML llama.cpp fork, release prism-b10685 (`7dffb15`), linux-cuda-12.4
- patched: the same fork at `7dffb15` plus one 15 line commit (`254725c6a`,
  `Fix: apply the Hadamard inverse to token embeddings in the qwen35 MTP graph`),
  built with `-DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=86`, reported as build 10686

Files:

- `Ternary-Bonsai-2-27B-PTQ1_0-mtp.gguf` (7,012,820,512 bytes, 867 tensors): the
  16 tensor head, including a donor copy of the embedding table as
  `blk.64.nextn.embed_tokens.weight` (Q4_K, 682 MiB). Loads on the prebuilt fork.
- `Ternary-Bonsai-2-27B-PTQ1_0-mtp-lean.gguf` (6,297,658,848 bytes, 866 tensors):
  the 15 tensor head without the embedding copy. Needs the patched fork.

## Identity (temperature 0, top_k 1, 300 tokens, thinking off)

| prompt | flag off run 1 vs run 2 | flag off vs flag on (n-max 1, 2, 3, prebuilt and patched) |
| --- | --- | --- |
| code | identical, 1024 bytes | differs from byte 216 (token 52) |
| prose | identical, 945 bytes | differs from byte 58 (token 14) |
| bash | identical, 1076 bytes | differs from byte 99 (token 24) |

Every flag-on arm produced the same three texts (sha256 `2ff5fe93`, `591a3caa`,
`53ac46fa`), so the divergence is deterministic. At each divergence the flag-off
top two candidates are close: code ` combines` -0.884 vs ` merges` -1.009,
prose ` data` -1.386 vs ` memory` -1.399, bash `\n` -0.827 vs `\n\n` -0.931
(natural log probabilities, server logprobs). The flag-on arm picked the runner
up in all three. `tools/batch_numerics.py` reproduces the flip without any
speculative decoding: replaying the same prefix so that the last 1, 2, 3, 4 or 8
tokens are evaluated in one batch moves the prose top two to
` data` by 0.003 (batch 1), ` memory` by 0.021 (batch 2 and 3), ` data` by
0.0005 (batch 4), ` memory` by 0.009 (batch 8). The fork's CUDA kernels are
not batch-size invariant on this model, and speculative verification always
runs a 2 or 3 token batch. Identity at temperature 0 therefore fails, and the
speed figures below are throughput observations, not a lossless speed claim.

Same test with flash attention off and f16 K/V (16384 context, both arms
`-fa off -ctk f16 -ctv f16`, flag arm n-max 1): prose identical (157 tokens),
code differs at token 74 (` efficient` -1.241 vs ` an` -1.263), bash differs at
token 179 (` close` -0.814 vs ` create` -0.827). Changing flash attention and
the K/V type also moves the flag-off text itself (all three prompts differ
between the two flag-off configurations), which is the same near-tie effect.

## Why the acceptance does not turn into speed

`llama-bench` on the merged file, prebuilt fork, default 4096 context, `-fa 1 -ctk q4_0 -ctv q4_0`:

| test | tok/s | ms per batch | vs one token |
| --- | ---: | ---: | ---: |
| tg32 (one token per step) | 26.02 | 38.4 | 1.0x |
| pp1 | 23.35 | 42.8 | |
| pp2 | 32.41 | 61.7 | 1.6x |
| pp3 | 32.24 | 93.0 | 2.4x |
| pp4 | 34.59 | 115.6 | 3.0x |
| pp8 | 52.67 | 151.9 | 4.0x |
| pp16 | 100.07 | 159.9 | 4.2x |

Verifying 2 drafted tokens (a 3 token batch) costs 2.4 single-token steps on
PTQ1_0, so even 0.9 acceptance cannot pay for it; verifying 1 draft (a 2 token
batch) costs 1.6 steps and yields 1.9 tokens at 0.9 acceptance, which is the
small win seen at n-max 1. For comparison, a standard quant of the same
architecture on the same card and binary (Qwen3.5 9B Q4_0, diagnostic only):
pp1 18.8 ms, pp2 19.9 ms (1.06x), pp3 20.2 ms (1.07x), pp4 22.4 ms (1.19x),
tg32 58.9 tok/s. The poor small-batch scaling is specific to the PTQ1_0 CUDA
mat-vec path, not to the architecture.
